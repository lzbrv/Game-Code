# Git, GitHub and Unreal — read this before your first commit

Repo: **https://github.com/lzbrv/Game-Code**

If you have used Git on a normal software project, most of your instincts transfer. The ones that
do not transfer are the ones that will cost you a weekend. This document is about those.

**The one-sentence version:** in Unreal, source code merges fine and content does not merge at all,
so the team uses branches for code and *file locks* for content, and never the other way round.

---

## 1. Why Unreal breaks the normal Git workflow

Git's entire value proposition is three-way merge on text. Unreal's content is not text.

A `.uasset` or `.umap` is an **opaque binary blob**: a serialised graph of engine objects, with
internal offsets, an import/export table, and version headers. Consequences, all of them hard:

- **You cannot diff it.** `git diff` on a `.uasset` tells you "binary files differ." That is all
  you will ever get. You cannot review a content change in a pull request.
- **You cannot merge it.** There is no three-way merge for a binary graph. If two people edit the
  same level, Git will report a conflict and your only options are *take mine* or *take theirs*.
  One person's work is deleted. Not "merged badly" — deleted.
- **Every save rewrites the whole file.** Move one actor in a level and the entire `.umap` is
  rewritten. Git stores a complete new copy of every version. A 40 MB level edited daily is over a
  gigabyte of history in a month.
- **Assets reference each other by path, opaquely.** Renaming an asset in Finder, or resolving a
  conflict by picking the "wrong" side, silently breaks references inside *other* binary files that
  Git cannot show you.

So the workflow every Unreal team converges on is:

1. **Git LFS** — keep the giant binaries out of the Git object database, so the repo stays clonable.
2. **File locking** — make it *impossible* for two people to edit the same asset at once, because
   after the fact there is no fix.
3. **Branches for C++, not for content.** Code merges. Content does not. Treat them differently.

This is not us being cautious. It is the reason most Unreal studios eventually leave Git entirely
(see §7).

## 2. What to commit, and what must never be committed

### Commit

| Path | Why |
|---|---|
| `Trace.uproject` | Project descriptor. Watch `EngineAssociation` — see §8. |
| `Source/**` | All C++, `.Build.cs`, `.Target.cs`. This is the actual work. |
| `Config/*.ini` | Project settings, gameplay tunables, input config. **Text — merges fine.** |
| `Content/**` | Assets. Via LFS. For Trace this is one empty `Arena.umap`. |
| `Scripts/**`, `docs/**`, `README.md` | Text. |
| `.gitignore`, `.gitattributes` | Critical. Commit these **first**, before anything else. |
| `Plugins/**` (source of plugins we author) | Same rules as `Source/`. |

### Never commit — all of it is generated

| Path | What it is |
|---|---|
| `Binaries/` | Compiled `.dylib`/`.dll`. Regenerated by every build. Platform-specific, huge, and a guaranteed conflict on every push. |
| `Intermediate/` | Object files, generated reflection headers (`*.generated.h`), UBT scratch. |
| `DerivedDataCache/` | Compiled shaders and cooked intermediate data. Can reach tens of GB. |
| `Saved/` | Logs, crash dumps, autosaves, per-user config, screenshots. |
| `Build/` | Packaging staging output. |
| `*.xcodeproj`, `*.xcworkspace`, `*.sln`, `.vs/`, `.idea/` | IDE project files — **generated** from `Source/*.cs`. Everyone regenerates their own with `Scripts/build.sh --projectfiles`. |
| `.ue-root` | Your personal engine path, read by `Scripts/_trace_common.sh`. Machine-specific by definition — the whole point is that it is *not* shared. |
| `.DS_Store` | macOS junk. Please. |

**These four directories are the whole reason Unreal repos explode.** They are recreated from
source, always, on every machine. If you ever suspect they are dirty, `rm -rf Binaries Intermediate
DerivedDataCache Saved`, regenerate project files, rebuild. You cannot lose work that way — nothing
in there is authored.

The repo already contains a `.gitignore` covering all of the above. Do not "fix" it by adding
`Binaries/` back because a build failed. It failed for a different reason.

If you have already committed one of them by accident, see §10.

## 3. Git LFS — setup

**LFS replaces large files in the repo with a ~130-byte text pointer**, and stores the real bytes
on a separate server. Your clone stays small; `git log` stays fast; you still `git add`/`commit`/
`push` normally.

### Per machine, once

```bash
brew install git-lfs
git lfs install          # installs the smudge/clean filters into your ~/.gitconfig
```

**Run this before you clone.** Clone first and LFS files arrive as pointer text, and Unreal fails
to load them with errors that do not mention LFS at all. (Fix: `git lfs install && git lfs pull`.)

After cloning, `Scripts/setup-lfs.sh` does the rest and checks its own work: verifies `git-lfs` is
installed, installs the filters if they are missing, lists the tracked patterns, and pulls the real
bytes. `--verify` reports without changing anything. It never rewrites history — if it finds
binaries that were committed outside LFS it prints the `git lfs migrate` command rather than
running it, because that one requires the whole team to agree first (§10).

### Per repo, once — already done for Game-Code

`.gitattributes` at the repo root declares which extensions go to LFS and which are lockable.
Here is the shape of it, so you understand what you are looking at:

```gitattributes
# <ext> filter=lfs diff=lfs merge=lfs -text   → store in LFS, never try to diff or merge it
# lockable                                     → checked out READ-ONLY until you take a lock

*.uasset  filter=lfs diff=lfs merge=lfs -text lockable
*.umap    filter=lfs diff=lfs merge=lfs -text lockable
*.fbx     filter=lfs diff=lfs merge=lfs -text lockable
*.png     filter=lfs diff=lfs merge=lfs -text lockable
*.wav     filter=lfs diff=lfs merge=lfs -text lockable
# ... plus the other binary media extensions

# Explicitly NOT lfs, NOT lockable — these are text and must merge normally:
*.ini     text
*.cpp     text
*.h       text
*.cs      text
```

Two things to internalise:

- **`-text` is not decoration.** It disables newline conversion. Without it Git will happily
  corrupt a binary file by rewriting bytes that look like CRLF.
- **`lockable` makes the file read-only in your working tree.** You physically cannot edit it until
  you take a lock. That is the point: the enforcement happens *before* the conflict, because after
  the conflict there is no remedy. Unreal will show the asset as read-only and refuse to save it.

To add a new binary type later:

```bash
git lfs track "*.psd"     # appends a rule to .gitattributes
# then hand-edit .gitattributes to add `lockable` if it's an editable source asset
git add .gitattributes
git commit -m "Track .psd in LFS"
```

**`.gitattributes` only applies to files added *after* it is committed.** Committing a binary
before the rule exists puts it in Git proper, permanently, until someone rewrites history.
This is why `.gitattributes` must be the first commit in the repo.

### Verify it is working

```bash
git lfs ls-files            # lists files actually stored in LFS
git lfs status              # what's staged, and whether it's going to LFS
git check-attr -a Content/Maps/Arena.umap   # should show filter: lfs, lockable: set
```

If `git lfs ls-files` is empty but you have `.uasset` files committed, they went in as raw Git
objects. Stop and fix it (§10) before the repo grows.

## 4. The locking workflow

This is the part that replaces branching for content. It takes ten seconds and it prevents the one
failure mode that has no recovery.

```bash
# BEFORE you open an asset to edit it:
git lfs lock Content/Maps/Arena.umap

# See who holds what, across the whole team:
git lfs locks

# Edit, save, commit, push as normal:
git add Content/Maps/Arena.umap
git commit -m "Arena: widen the endzones"
git push

# THEN release it — immediately. Do not hold locks overnight.
git lfs unlock Content/Maps/Arena.umap
```

The rules, in order of importance:

1. **Lock before you open the asset in the editor, not before you save.** By the time you save you
   have already done the work someone else is also doing.
2. **Push before you unlock.** Unlocking before pushing means someone locks it, edits the old
   version, and you both have divergent binaries.
3. **Unlock as soon as you have pushed.** A forgotten lock blocks a teammate silently.
4. **`git pull` before locking.** You want the latest version of the file you are about to become
   the sole author of.
5. If someone else holds the lock: **wait, or talk to them.** Do not force it.

Force-unlocking someone else's lock (only when they are unreachable, and say so in chat first):

```bash
git lfs locks                            # get the lock ID
git lfs unlock --id=<id> --force
```

That does not merge anything. It just makes the file writable again. Whoever was editing it is
about to have a bad time — hence "talk first."

### From inside the Unreal editor

Unreal has a built-in Git source-control provider that drives all of this from the UI, which is
much more pleasant than remembering to run commands.

**Revision Control** (bottom-right of the editor) → **Connect to Revision Control** →
Provider: **Git**. Point it at the repo root, and enable **"Use Git LFS 2 File Locks workflow"**.

After that, opening a locked-by-someone-else asset shows a lock badge, and checking out an asset
takes the LFS lock automatically. Everyone should turn this on. It is the difference between a
policy people follow and a policy people forget at 1 a.m.

## 5. GitHub's LFS quota — the numbers, and the wall

Verified against GitHub's current billing documentation (August 2026). **These numbers changed
recently** — a lot of blog posts and older docs still quote 1 GiB, which was the figure for years.

| Plan | Included LFS storage | Included LFS bandwidth |
|---|---|---|
| **Free** | **10 GiB** | **10 GiB / month** |
| **Pro** | **10 GiB** | **10 GiB / month** |
| Team | 250 GiB | 250 GiB / month |
| Enterprise Cloud | 250 GiB | 250 GiB / month |

Billing model: GitHub **removed the pre-paid $5 data packs** and replaced them with **metered
billing** — you pay for what you use past the included amount, at roughly **$0.07 per GiB-month of
storage** and **$0.0875 per GiB downloaded**. Check the current rate on GitHub's pricing page
before budgeting; per-GiB rates are the kind of thing that moves.

Also enforced, independent of quota:

- **Files over 100 MiB are rejected outright** if pushed outside LFS (warning above 50 MiB).
- **Max single LFS file: 2 GB on Free/Pro** (4 GB Team, 5 GB Enterprise).
- GitHub recommends keeping repositories under 1 GB and strongly discourages going past 5 GB.

### Why 10 GiB sounds like plenty and is not

Three things eat it far faster than people expect:

1. **Storage counts every version, forever.** LFS storage is the sum of every version of every
   tracked file across your entire history. Delete a 200 MB asset today and you still pay for it —
   the old versions are still in history. Iterating on one level fifty times means fifty copies.
2. **Bandwidth counts every download.** A fresh clone by each of four people, plus every CI run,
   plus every `git lfs pull`, all count. Four people cloning a 2 GiB project once each is 8 GiB —
   80% of a month's free bandwidth, gone in an afternoon.
3. **Real art is big.** One 4K texture set is ~100 MB. A character with textures is ~500 MB. A
   handful of audio stems and a few weeks of level iteration puts you past 10 GiB comfortably
   inside a month of real production.

**Trace is fine right now** — it is deliberately asset-free, so LFS holds essentially one empty
`.umap`. You will not notice the quota this month. **You will notice it the week someone imports
real art.** Treat the current comfort as temporary.

Check usage: GitHub → Settings → **Billing and plans** → look for Git LFS Data. Watch it. Running
out of bandwidth mid-month means **nobody on the team can clone or pull LFS content until the quota
resets or someone pays.** That is a hard stop on the whole team, and it always happens at the worst
moment.

## 6. Habits that keep you under the quota

- **Never track a generated file in LFS.** Re-read §2. `Intermediate/` and `DerivedDataCache/` in
  LFS is the classic way to burn a quota in one push.
- **`git clone --depth 1` for a machine that only needs to build**, and configure
  `GIT_LFS_SKIP_SMUDGE=1 git clone` then `git lfs pull` if you want history without every binary
  version.
- **Don't commit intermediate art.** Import the final asset. The 40 iterations live in Dropbox or
  your local disk, not in history.
- **Don't commit test/scratch levels** to `main`. Every save is a full new copy.
- **One person, one asset, one session.** Locking enforces it, but the discipline is what makes it
  cheap.

## 7. When you outgrow GitHub LFS

You will, if this project keeps going. The three real options, honestly compared:

### a) Stay on GitHub, pay for LFS

Simplest. Metered billing means no plan change is needed — usage past 10 GiB just bills. Realistic
for a small project with modest art. Still has the fundamental problem that Git's data model was
never designed for binary game content: clones stay slow, history stays enormous, and locking is a
bolt-on rather than a first-class concept.

### b) Perforce / Helix Core — what most Unreal teams end up on

**P4 is free for up to 5 users and 20 workspaces**, self-hosted, with no feature limits and no time
limit. Four people fits with room to spare. (Past 5 users / 20 workspaces the free tier collapses to
a 1,000-file limit, so it is genuinely 5 users, not "5 users but you can cheat.")

Why studios use it:
- **Locking is native**, not an extension. Checkout-before-edit is the default model.
- **Built for huge binary repos.** Sparse workspaces mean an artist syncs only the art they need,
  not 200 GB of everything.
- **Unreal's deepest integration by far.** Epic themselves ship on Perforce; the editor's Perforce
  source-control provider is the best-supported one, and features like OFPA (One File Per Actor)
  and virtual assets assume a Perforce-shaped workflow.

Cost: you must run a server (a small cloud VM, or one always-on machine), and the mental model is
genuinely different from Git — centralised, checkout-based, no cheap local branching. Plan a day to
set it up and a week for everyone to stop reaching for `git status`.

**Common hybrid, and a good one: code stays in Git/GitHub, content moves to Perforce.** You keep
PRs and code review where they work and put binaries where they work.

### c) Diversion

A newer hosted VCS built specifically for game/creative teams, with a first-party Unreal plugin.
**Free tier is generous — around 100 GB of storage and up to 10 users** (indie tiers vary; check
their pricing page, it has moved more than once). Cloud-hosted, so no server to run, and the
mental model is closer to Git than Perforce is.

Trade-off: it is a much younger product than Perforce with a smaller community, and you are
depending on a startup's pricing staying reasonable. Worth a look before committing to running a
Perforce server, especially given four people and no ops appetite.

### Recommendation for Trace, right now

**Stay on GitHub + LFS + locking.** The project is asset-free by design and the quota is not close
to binding. Revisit the moment someone says the words "I'm importing the character model." Migrating
later is annoying but entirely doable; migrating *after* burning three months of LFS bandwidth is
annoying *and* expensive.

## 8. The `EngineAssociation` gotcha

Open `Trace.uproject`. Line two or three:

```json
"EngineAssociation": "5.8",
```

That string tells Unreal which engine to open the project with. It takes two forms:

- **Launcher-installed engine → a plain version string**, e.g. `"5.8"`. Portable. Works on every
  machine, every OS, regardless of where the engine is installed. **This is what we use.**
- **Source-built engine → a machine-local GUID**, e.g. `"{5FFE8984-EA6F-49EC-859E-6CB8C10FE54D}"`,
  resolved through a registry that lives on *that one machine* (on macOS:
  `~/Library/Application Support/Epic/UnrealEngine/Install.ini`).

**The failure:** somebody opens the project with a source build, or a differently-registered
engine, and **the editor silently rewrites `EngineAssociation` to their machine-local GUID.** They
commit `Trace.uproject` along with their real work. Everyone else pulls, and gets:

> The engine associated with this project is not installed

…or the engine-picker dialog, or a "convert project?" prompt that will happily upgrade every asset
in the repo to an incompatible version.

**The rules:**

1. `"EngineAssociation"` stays `"5.8"`. It is effectively a protected line.
2. **Any diff on that line is a blocked change.** If `git diff Trace.uproject` shows it changed,
   revert that hunk before committing:
   ```bash
   git diff Trace.uproject          # check before every commit that touches it
   git checkout -- Trace.uproject   # if the only change is EngineAssociation
   ```
   Reverting the whole file is safe as long as you did not intentionally add a plugin or module.
   If you did, edit by hand and keep the association line.
3. **Never put a filesystem path there.** It "works" for exactly one person.
4. If it has already been committed wrong: fix the line, commit, and tell everyone to pull *before*
   they open the editor again.

### Everyone runs the same engine version — non-negotiable

Beyond `EngineAssociation`, mixed engine versions across a team cause:

- **Silent asset upgrades.** Open a `.umap` in a newer engine and save it: the file is now written
  in the newer asset version and **older engines cannot open it at all**. Not "with warnings" —
  at all. One person on 5.8.2 can lock the entire team out of the level, in one save, with no
  warning that they did anything.
- Different generated reflection code, so binaries and DDC are mutually useless.
- Bug reports nobody else can reproduce.

So: pin the exact 5.8.x build (see [SETUP.md](SETUP.md#5-install-unreal-engine-58--and-why-we-pin-it)),
turn off launcher auto-update, and upgrade **as a team, deliberately, on a branch**, never
individually.

## 9. A branching model for four people

The asymmetry drives everything: **C++ merges, content does not.**

```
main          ← always builds, always runnable. Protected.
 ├─ feat/<name>/<thing>    short-lived C++ branches. PR into main.
 └─ (content changes)      committed to main directly, under an LFS lock.
```

### For C++ — normal Git, use it properly

```bash
git checkout main && git pull
git checkout -b feat/greg/trail-trip-test

# ... work, commit in small pieces ...

git push -u origin feat/greg/trail-trip-test
gh pr create --fill                  # or open a PR in the browser
```

- **Keep branches short.** A day or two. A week-old Unreal branch is a merge you will regret,
  especially if it touched `Source/**` layout or `.Build.cs`.
- **PRs get reviewed.** With four people, one approval is enough. The point is that someone else has
  seen the netcode, not ceremony.
- **Rebase or merge, pick one, write it down.** Suggested: `git pull --rebase` on feature branches,
  merge commits into `main`. Linear enough to read, no force-pushes to shared branches.
- Squash-merge is fine and keeps `main` readable.

### For content — the opposite

- **Do not branch content.** A branch containing an edited `.umap` cannot be merged; it can only
  overwrite. Branching content creates the exact conflict that locking exists to prevent.
- **Lock → pull → edit → commit → push → unlock**, straight onto `main`.
- If a feature genuinely needs both code and a new asset, add the asset on `main` first (locked,
  quick), then build the code on a branch against it.

### Rules the whole team agrees to

1. **`main` always builds.** If you break it, fixing it is your only priority.
2. **Never force-push `main`.** Never rewrite shared history — with LFS involved, history rewrites
   can orphan objects and break other people's clones in confusing ways.
3. **`git pull` before you start. Every time.** Especially before taking a lock.
4. **Never commit `Binaries/`, `Intermediate/`, `DerivedDataCache/`, `Saved/`.**
5. **Never commit an `EngineAssociation` change.**
6. **Announce engine upgrades**, and do them together.
7. **Config `.ini` files are text and merge fine** — but two people tuning the same
   `[/Script/Trace.TraceSettings]` values will produce noisy conflicts. Coordinate; they are tiny
   and easy to resolve, just don't be surprised.

### Suggested GitHub settings for the repo

- Branch protection on `main`: require a PR, require 1 approval, block force-push.
- Do **not** enable "require linear history" if you plan to merge — it fights the workflow above.
- Turn on **Settings → General → Archive**, no. Turn on nothing else. Keep it simple.

## 10. Recipes for when it has already gone wrong

### "I committed `Binaries/` / `Intermediate/`"

If it is not yet pushed, or is on your own branch:

```bash
git rm -r --cached Binaries Intermediate DerivedDataCache Saved
git commit -m "Remove generated directories from tracking"
git push
```

`--cached` removes them from Git only — your local files stay, and your build is unaffected. The
files remain in history (and so still count toward repo size), but they stop growing. Only rewrite
history if the size is actually a problem, and only with everyone offline (see below).

### "I committed `.uasset` files before `.gitattributes` existed"

They are in Git proper, not LFS. Convert them:

```bash
git lfs migrate import --include="*.uasset,*.umap,*.fbx,*.png,*.wav" --everything
git push --force-with-lease --all
git push --force-with-lease --tags
```

**This rewrites history.** Every other person must then re-clone, or reset hard to the new
`origin/main`. Coordinate it: everyone pushes their work first, then one person migrates, then
everyone re-clones. Do it while the repo is small — which is now.

### "My content files are a few lines of text starting with `version https://git-lfs...`"

You cloned before `git lfs install`. Those are the pointer files.

```bash
git lfs install
git lfs pull
```

### "Someone else has the level locked and they're asleep"

Work on something else. Genuinely — that is the correct answer, and it is why locks should be short.
If it is blocking and they are unreachable, post in chat, then:

```bash
git lfs locks
git lfs unlock --id=<id> --force
```

### "Merge conflict on a `.uasset`"

There is no merge. Decide, explicitly, whose version survives:

```bash
git checkout --ours   Content/Path/Asset.uasset    # keep the version on your current branch
# or
git checkout --theirs Content/Path/Asset.uasset    # keep the incoming version
git add Content/Path/Asset.uasset
```

Then **the person whose work was discarded redoes it.** There is no third option. If this happens
more than once, locking is not being used.

### "Everything is broken and I don't know why"

```bash
git status                                       # is your tree actually clean?
rm -rf Binaries Intermediate DerivedDataCache    # generated; safe to delete
# regenerate project files and rebuild — see SETUP.md §7/§8
```

Nothing in those directories is authored. You cannot lose work this way.

## 11. First-time repo bootstrap

`lzbrv/Game-Code` is currently empty. Doing this in the right order matters, because
`.gitattributes` must exist **before** any binary is added, or the binary bypasses LFS forever.

```bash
cd ~/trace

git lfs install
git init -b main

# 1. LFS rules and ignores FIRST, on their own commit.
git add .gitattributes .gitignore
git commit -m "Add .gitattributes (LFS + locking) and .gitignore"

# 2. Verify the rules actually apply before adding anything binary.
git check-attr -a Content/Maps/Arena.umap
#   expect: filter: lfs / diff: lfs / merge: lfs / text: unset / lockable: set

# 3. Now everything else.
git add .
git status                       # eyeball it: no Binaries/, Intermediate/, DerivedDataCache/, Saved/
git commit -m "Trace: C++ prototype, arena built at runtime, no binary assets"

# 4. Confirm any binaries went to LFS, not to Git.
git lfs ls-files                 # lists Content/Maps/Arena.umap once that level exists

# 5. Push.
git remote add origin https://github.com/lzbrv/Game-Code.git
git push -u origin main
```

Note on `Content/Maps/`: the directory is held open by a `.gitkeep` file, because Git tracks files
and not directories. If you bootstrap the repo before running `Scripts/generate-map.sh`, that
`.gitkeep` is all that is in there and `git lfs ls-files` is legitimately empty. Whoever generates
`Arena.umap` first commits it — under a lock, and then never touches it again, since it is
permanently empty by design.

Then, in the GitHub UI: **Settings → Collaborators** → add the other three with **Write** access.
Write access is required to take LFS locks — read-only collaborators cannot lock, which defeats
the whole workflow.

Everyone else:

```bash
git lfs install                  # BEFORE cloning
git clone https://github.com/lzbrv/Game-Code.git ~/trace
cd ~/trace
Scripts/setup-lfs.sh             # verifies the filters engaged and pulls the binaries
```

Then [SETUP.md](SETUP.md) from §7.

## 12. Cheat sheet

```bash
# Daily
git pull                                  # always, before you start
git status
git add -p                                # stage in reviewable pieces
git commit -m "..."
git push

# Content
git lfs lock   Content/Maps/Arena.umap    # BEFORE opening it in the editor
git lfs locks                             # who holds what
git lfs unlock Content/Maps/Arena.umap    # AFTER pushing

# Content — /Game/Maps/Arena_Baked only. It has One File Per Actor on, so the
# level is a tiny .umap plus one .uasset per actor. Lock the ACTOR, not the map:
# that is the whole point of the migration, and locking the .umap blocks nobody.
# Find the actor by its LABEL in the World Outliner (Wall_North_01, Cover_037)
# and let the editor's source control integration lock the file behind it.
git lfs lock Content/__ExternalActors__/Maps/Arena_Baked/<xx>/<yy>/<guid>.uasset

# LFS health
git lfs ls-files                          # what's actually in LFS
git lfs status
git lfs pull                              # fetch binaries for the current checkout
git check-attr -a <file>                  # why is this file being treated that way

# Code branches
git checkout -b feat/<name>/<thing>
git pull --rebase origin main
gh pr create --fill

# Panic
git diff Trace.uproject                   # did EngineAssociation move?
rm -rf Binaries Intermediate DerivedDataCache
```
